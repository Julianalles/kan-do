# ADR 020: A floating Now window: a second Tauri window owned by Rust, with no access to the data file

## Status

Accepted (#383; decisions D1 to D8 in the issue body). The ADR number was taken as the next free one on `main` and may be renumbered at merge.

## Context

While a task sits in Jetzt and the user works in another app, the task and its timebox are out of sight. The design (a pill that floats over other apps, draggable, switchable in the settings) needs a second window. The app has one writer of the data file, guarded in Rust (ADR 011), and a webview that loads the whole app shell (stores, timers, menu, updater); a second webview that did the same would be a second writer and a second timer driver.

## Decision

- **Rust owns the window and its visibility** (`src-tauri/src/overlay.rs`). The window (label `overlay`, opened at the route `/overlay`) is created hidden once a snapshot with a Jetzt task arrives while the setting is on, shown iff the setting is on, a task is shown and the pill has reported ready (`overlay::should_show`), whichever window has the focus (#436, see below), hidden otherwise, destroyed when the setting turns off and with the main window (a hidden window left alive would keep the process running after the last visible window closed). Rejected: a window made from JS (needs `core:webview:allow-create-webview-window`, and the show/hide decision would run in a webview macOS may throttle while it is covered).
- **The main window publishes a snapshot, Rust relays it.** `overlay_sync(enabled, snapshot)` carries `{ taskId, title, timeBoxSeconds, spentSeconds, at, running, locale }` (or `null`), sent on every change of what the pill shows and at the 10 s time checkpoint, never per second. The pill counts on by the wall clock from `at` (`lib/nowWindow.ts`), so a throttled main window cannot freeze it. The pill's clicks go back as `overlay_action(kind, taskId)` with `kind` in `OVERLAY_ACTIONS` (`open`, `toggle-pause`, `done`): `open` is handled in Rust, the other two reach the main window as the event `overlay://action`, which ignores a task that is no longer the Jetzt task. Pause moves the task to Wartet (#405; first: the existing timer stop, runtime-only); done is the board's own completion path. Rejected: the pill reading the persisted store (a second writer on the guarded data file).
- **The pill never touches data.** `app.vue` is a thin switch (`lib/overlayWindow.ts`: Tauri and path `/overlay`) between the pill and the app shell (`components/AppShell.vue`, the former `app.vue`); every client plugin that loads data, starts work or checks for updates returns early in the pill window (`tests/config/overlay-contract.test.ts` lists `plugins/` and fails for a new plugin that neither guards nor is listed as harmless); and Rust's `data_*` commands refuse a window that is not `main`. The pill needs no store: it takes the language from the snapshot.
- **The position is machine-local.** `overlay-window.json` (`{ x, y }`, physical pixels) in the app config dir, written debounced while the user drags. The data file can sit in iCloud and be opened on Macs with other displays, so a position stored there would travel to a screen it does not fit. A saved spot is clamped into the work area (`Monitor::work_area`: no menu bar, no Dock) of the monitor that holds it and falls back to the bottom right of the primary one when it is on no display (`resolve_position`, unit-tested). Only the on/off setting is persisted state: `settings-store.floatingNowEnabled`, additive, default on.
- **Transparent window, system glass.** `app.macOSPrivateApi` and the `tauri` crate feature `macos-private-api` (the build refuses one without the other): kan-do ships a notarized DMG, not through the App Store. The window is not focusable (`focusable(false)`), always on top, on all spaces, and `accept_first_mouse` so the first click acts. Since #436 the window is exactly the pill (340 x 60 pt, no margin) and is built with Tauri's window effects (`WebviewWindowBuilder::effects`: `LiquidGlassRegular`, falling back to the `HudWindow` vibrancy material before macOS 26, a capsule, corner radius 30, state `Active` because the pill is never the key window), with the system's own window shadow. The system renders the glass, so it follows the user's Liquid Glass (Clear/Tinted) and Reduce Transparency settings without kan-do reading them; no new crate (`window-vibrancy` is already Tauri's). Rejected: CSS `backdrop-filter` (blurs only what the webview itself holds, never the apps behind the window) and a hand-written `NSGlassEffectView`.
- **Shown whichever window has the focus (#436, replaces the first rule "hidden while Kan-Do is in front").** Pressing the pill activates kan-do, so under the first rule the main window gained the focus and the pill hid under the pointer: it could not be moved and seemed to vanish. It is now visible as long as the setting is on and a task is shown; with Kan-Do in front it floats over the board and the user moves it or turns the setting off. A click without travel still brings Kan-Do forward; a drag does not. The label colours follow the system's light or dark appearance (the pill sits on arbitrary wallpapers), the accents are the app's primary and warning steps.
- **Least privilege.** `capabilities/overlay.json` grants the `overlay` window `core:event:default` and `core:window:allow-start-dragging` only; no new CSP host. The pill drags with `startDragging()` after 3 px of pointer travel, because a `data-tauri-drag-region` element cannot be clicked.

## Consequences

- A second webview costs memory; it exists only while the setting is on and a Jetzt task has been seen.
- Over another app's full-screen space the pill does not show (Tauri 2.12 does not expose the collection behaviour that needs); hover on an inactive window, the first-click behaviour and the drag feel are WKWebView matters checked by hand.
- The window is macOS-tested only; the setting is hidden on the web.
- Pause (#405) moves the task to the top of Wartet (a status move, written to a connection like any move) and the pill keeps it, paused, until resume, done, a card in Jetzt, the task leaving Wartet, the setting off or a restart (a runtime pin in `useNowWindowSync`, no Rust change). The Jetzt card has no paused state: a card in Jetzt is counting. This replaces the first design, where pause left the task in Jetzt with a stopped timer. The card's own "arrival" motion of #405 (a set-down and a pause-glyph layer that played when the user came back to the app) was removed in #436: the card moves from Jetzt to Wartet like any other move.
- The pill's timer line (#436) is a countdown: it starts full and shrinks with the time left, primary until 80 % of the timebox is spent and warning above it (the app's `getTimeboxRingColor`); a task without a timebox has no line and the time label counts up. The in-app bar still grows with the time spent (#450 aligns it).
- A new plugin is guarded with `isOverlayWindow()` or listed as harmless; a new `data_*` command takes `window: tauri::Window` and calls `ensure_main_window`.
