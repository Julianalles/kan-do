# ADR 021: The public web instance runs on Cloudflare Workers, behind a token gate

## Status

Accepted (epic #279; this ADR comes with its first slice #502; the proxy guards #503 are in it, the web CSP #504 is in it). The ADR number was taken as the next free one on `main` and may be renumbered at merge.

## Context

kan-do's web build ran on Vercel only. The homepage's secret launch (jaylouiz/jwue-homepage, milestone M2) needs the app reachable by invited people and by nobody else, on a free plan, next to the homepage's own Worker `www` on the same Cloudflare account. The app is a single-page app (`ssr: false`); only `/api/*` runs server code (the Notion proxy, the feedback relay, an unused Todoist token route). Nothing is stored server-side: user data lives in the browser's localStorage and in the user's own Notion or Todoist.

## Decision

- **Worker `kando` on `https://kando.julius-wuestefeld.workers.dev`** (Workers Free). The custom domain `kando.julius-wuestefeld.de` follows with the homepage's public launch (jwue-homepage M3) and is not part of this ADR. The gate cookie is `__Host-` bound, so the move needs no gate change.
- **Build: Nitro's `cloudflare_module` preset** (`npm run build:cloudflare`: `NITRO_PRESET=cloudflare_module`, and `NUXT_PUBLIC_FEEDBACK_RELAY_URL=/api/feedback` so the instance's feedback dialog posts to its own relay). `wrangler.jsonc` serves `.output/public` as Workers assets (static requests are free of charge) and runs the Nitro handler for `/api/*` and the SPA shell. `compatibility_flags: ["nodejs_compat"]` gives `Buffer` and `process.env` (vars and secrets). The desktop build (`npm run generate`, `src-tauri`) and the Vercel build are unchanged.
- **The gate is a Worker entry that wraps Nitro's built handler** (`worker/index.ts`, logic in `worker/gate.ts`, mirrors the homepage's gate), with `assets.run_worker_first: true` so static files pass it too. Rejected: a Nitro server middleware (Nitro's Cloudflare handler answers public asset URLs from the assets binding before any middleware, so `/_nuxt/*.js` would leak); Cloudflare Access (needs a zone and Zero Trust, and the user chose a shared token).
- **The token** is one shared secret, `GATE_SECRET` (the homepage's value, user decision 2026-11-18). A valid `?secret=` sets an HttpOnly, Secure, SameSite=Lax cookie `__Host-kd_gate` (the sha256 of the secret, 90 days) and redirects to the same URL without the parameter. Without it: 401 with a plain "Private preview" page (no app HTML, no script, no asset). `POST /api/feedback` and its `OPTIONS` preflight are exempt (desktop builds post without a cookie; the relay has its own hourly cap); `/api/notion/*` stays gated. While gated every response carries `X-Robots-Tag: noindex, nofollow` and `/robots.txt` disallows everything. `vars.GATE` is `"on"` in `wrangler.jsonc` (the single source: a fresh deploy is gated, and a dashboard toggle would be reset by the next deploy); `"off"` opens the app for the public launch (jwue-homepage #34), a deliberate change of that line through a PR; a missing `GATE_SECRET` with the gate on denies every request. A secret never appears in an issue, PR, commit or log.
- **The Notion proxy has three guards** (#503, all stateless, `/api/notion/*` only, active with the gate off too; order gate → origin check → rate limit → app, `worker/pipeline.ts`):
  - *Token out of the URL.* The browser sends the Notion token as `Authorization: Bearer` (`NotionClientAPI.getProxyOptions`); the server routes read only that header and ignore a `?token=` (`validateRequest`, `notion-stub-failure`), so no token ends up in Cloudflare logs or analytics.
  - *Origin check* (`worker/guards.ts`): an `Origin` other than the Worker's own (`null` included), or `Sec-Fetch-Site` `cross-site` or `same-site`, answers 403 `FORBIDDEN_ORIGIN`, so no other website can use a visitor's browser as a Notion proxy. A request without `Origin` (curl, server to server) passes: this is no authentication (the token still is) and no defence against direct scripts. `/api/feedback` is open to every origin by design and not checked. The path is decoded, slash-collapsed and case-folded before matching, so `//api/notion/…` or `/api/%6Eotion/…` cannot skip the check.
  - *Rate limit* (#503, reworked in #508): a Durable Object, `NOTION_LIMITER` (`worker/limiter.ts`, `durable_objects` in `wrangler.jsonc`), one object per client counting 120 requests per 60 s, so the count is exact across isolates and locations; over it answers 429 `RATE_LIMITED` with `Retry-After: 60` (the client sleeps a `Retry-After` of up to 10 s before its one retry and throws a longer one at once, #507, so a create under the limit stays pending for the next push) The client is `CF-Connecting-IP`, an IPv6 address by its /64 (`clientKey`). Measured: loading a Notion board is 5-6 requests, a status move 2 (`tests/e2e/notion-proxy-token.spec.ts`), so normal use stays an order of magnitude below. A missing binding, a failing object or an exhausted Durable Objects Free quota lets the request pass: the guard never blocks the app by itself, so under a flood the Worker's own Free request quota is the last bound. **Why not the Workers Rate Limiting binding** (what #503 shipped): live on workers.dev (Free) it never limited, 1200 requests in 28 s from one IP against 120 per 60 s all reached Notion, with no error in Workers Logs; the code was right (`wrangler dev` blocks the 121st request). Cloudflare documents the binding as approximate, counted per location from a local, eventually consistent count that "can exceed your configured limit", and others report the same non-enforcement on workers.dev (cloudflare/developer-platform#123, open, no reply); Cloudflare's own advice for a strict limit is a Durable Object. Cost: one Durable Object request per `/api/notion/*` request (Free: 100,000 a day, as many as the Worker's own requests); the class is SQLite-backed (`new_sqlite_classes`, the only kind Free allows) and checkpoints its window there (first hit of a window, then every tenth, rounded up, so a restored count is at most 9 above the true one), because an idle object is evicted after about ten seconds and a client could otherwise reset its window by pausing; nothing of a client outlives its window: the first write of a window sets an alarm at the window's end that deletes everything the object stored (`alarm()`), so no row stays per client ever seen; and the object's name is no IP: `idFromName` gets an HMAC-SHA-256 of the client key (`limiterName`), keyed with the existing `GATE_SECRET` (no new secret; without it, the gate off or a test, a public constant keys it, so the name is still no plain IP and the alarm bounds its life; keep `GATE_SECRET` set after the public launch). An IP is personal data and the Worker stores nothing of a visitor (epic #279); the alarm leaves, per client, at most one window of a count under a pseudonym, and Cloudflare's own request logs hold IPs regardless. Switching back is a `ratelimits` line and a `deleted_classes` migration. Rejected: keeping the binding as well (a second guard that does not fire is a false assurance), a Cloudflare zone rule (needs the custom domain; revisit at M3), an allow-list of Notion paths (the routes are fixed actions, no caller-chosen URL reaches Notion). Live check after a deploy: from one IP `seq 1 400 | xargs -P 20 curl … /api/notion/databases` (gate cookie, dummy bearer, no `Origin`) shows 120 × 401, then 429s with `Retry-After: 60`; a request after 60 s passes again.
  - *Dev surface:* `/api/dev/*` and `/api/notion/ping` answer 404 on the built Worker, `/api/config/notion-key` only reports `hasKey`, and `NOTION_KEY` stays unset.
  - *Server logs* (#511): Workers Logs persist the console, so a route logs a failure only through `logServerError` (`server/utils/serverLog.ts`): one line `[server-error] route=<path> status=<n> code=<c>`, the code an allow-listed pattern, never the error object, its message, a body, a header, a token or the query string (which holds database and page ids). The dev-only Notion response dumps are deleted rather than gated, so no `NODE_ENV` value can switch them on. `tests/server/api/notion/log-privacy.test.ts` fails when a route logs a task title or a token; a new `console.*` in `server/` needs the same proof. Three more paths close the rest (#525, #530): (1) *Nitro's own error log.* Nitro's default handler logs an unhandled throw as `[request error] [unhandled] [METHOD] <full URL>` plus the raw error; the production build registers `server/error-handler.ts` as `nitro.errorHandler` (set in the `nitro:config` hook, not as a config key: a key makes Nuxt skip its own handler and with it the `/__nuxt_error` page and the `vary` header), which wraps Nuxt's handler: it logs only through `logServerError`, hands Nuxt's handler a `defaultHandler` with its log off and sends the built-in JSON itself where Nuxt's handler leaves a JSON request unhandled or throws (not registered under `nuxt dev`); the task routes also answer 400 `INVALID_JSON` for a mapping that is valid JSON but no object (`parseMappings`), so that case is no unhandled throw at all. (2) *The Notion SDK's logger.* Every client comes from `createNotionClient` (`server/utils/notionClient.ts`: `logLevel` error and a no-op logger; the SDK logs only at debug, info and warn, its WARN `request fail` quotes the request); a test fails when `new Client(` appears in `server/` elsewhere. The factory also turns the SDK's own retries off (`retry: false`, #539): the SDK would retry a 429 twice, honouring `Retry-After` up to 60 s each, so the proxy would spend Notion quota inside the limit window and answer after the browser's 10 s timeout; the proxy throws the first error, `handleNotionError` forwards `Retry-After` and the browser client is the one retry policy. (3) *Workers Logs.* `wrangler.jsonc` keeps them on with `redact_query_string: true` and `logs.invocation_logs: false` (sampling 1): what persists is the allow-listed `[server-error]` line and nothing of a request (no URL, query, header or IP of ours). The Worker's own entry code (`worker/`) logs only through `logWorkerError` (`worker/log.ts`, #540): a constant message plus the error's name when it is a plain identifier, never the error object, message, stack or cause; `worker/log.test.ts` fails when another file there calls `console.`. The live instance gives up the per-request invocation lines (path, status, CPU time, outcome); Cloudflare's dashboard request and error metrics are unaffected. Switching back is one line in `wrangler.jsonc` and a deploy. Rejected: observability off (an outage would leave no trace), lower sampling (still persists URLs for the sampled share). Unverified: the exact field list of a Cloudflare invocation log; check in the dashboard after the first deploy that a request leaves no line and a thrown route leaves one `[server-error]`.
- **Content Security Policy** (#504; the desktop's is ADR 012, the same trade-offs): the Worker sets `Content-Security-Policy`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer` on the app's `text/html` responses (`worker/csp.ts`, applied in `worker/pipeline.ts` behind gate and guards, so the gate's 401 page, its redirects and the guards' 403 and 429 are unchanged; JSON and assets get none). Policy: `default-src 'self'; script-src 'self' <hashes>; style-src 'self' 'unsafe-inline'; font-src 'self'; img-src 'self'; connect-src 'self' https://api.todoist.com; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'none'`. Notion and the feedback relay are same-origin on the instance (`/api/notion/*`, `/api/feedback`), so only Todoist (a webview-side `fetch`) is a second host. `script-src` carries the sha256 of the shell's two inline scripts (the import map and the `window.__NUXT__` config), which change with every build, and of the inline scripts the client injects at runtime through `useHead` (today one: Nuxt's built-in 404 page wires its "Go back" button; the shell cannot show it, so `csp-hashes.mjs` reads it from the built `_nuxt/*.js` chunks, #512): `nuxt.config.ts` prerenders `/200.html` for the Cloudflare preset (its build writes no HTML file; Nitro renders the same template per request), `scripts/csp-hashes.mjs` writes the hashes to `worker/csp-hashes.generated.json` (git-ignored; `build:cloudflare` runs it before the bundle check, which fails when the bundle lacks them), and `worker/index.ts` bundles them. `tests/config/web-csp.test.ts` fails when a built shell's inline script has no hash in the policy or the generated file holds a stale one, `worker/csp.test.ts` pins the directive list. Rejected: nonces (rewriting the HTML per request costs CPU on the free plan), a `_headers` file (no per-build hashes, skipped for Worker-served responses), hashing at request time. The web build has no feedback screenshot (native capture is desktop only, ADR 014), so `img-src` needs no `blob:` or `data:`; measured in Chromium against `wrangler dev`: the Local, Notion and Todoist boards, the feedback dialog with element pick, the settings pages, statistics and welcome raise no violation but the Todoist SDK's one `eval` probe (Todoist board only), an injected `<script>`, an inline event handler, a foreign `fetch` and a foreign image are blocked. **Not covered: Vercel**, which keeps serving the app without a CSP until a slice gives its build the same hash step (decision D2 of #504). Live checks after a deploy: curl shows the header on `/` and none on `/_nuxt/*.js` or `/api/*`; a browser session on the live URL has a clean console, an unknown path included (its 404 page still logs Nuxt's own `[NUXT_E1005]`, the `app:error` diagnostic of any 404, but no CSP violation).
- **No service worker.** The web build registers none, so a cached app shell cannot bypass the gate; a regression would show in `.output/public` (no `sw.js`) and in the code (`rg serviceWorker`).
- **No `NOTION_KEY`** on the instance, and the Notion stub stays off: `NODE_ENV` is inlined as production, `E2E_NOTION_STUB` and `NOTION_STUB_ENABLED` are never set as vars, `/api/dev/*` answers 404, `/api/notion/ping` is a 404 in production.
- **Pipeline: Workers Builds** (the homepage's setup): a push to `main` runs the build command `npm run build:cloudflare` and the deploy command `npx wrangler deploy` (`npm run deploy` is both in one for a manual deploy). The dashboard connection is a user step (Worker `kando` > Settings > Builds > Connect, a dashboard-created build token; the Worker, its secrets and the connection can equally be created through the Cloudflare API). Non-`main` branches get no Workers Builds build: `preview_urls` is off and a branch build would otherwise run the production deploy command. Vercel keeps `main`, `proto/*` and `dev` (previews, the dev instance), and its production deployment stays the feedback relay target of shipped desktop builds until #280 switches them.

- **The deployed Worker is `worker/index.ts`, never Nitro's own.** Under Workers Builds (`WORKERS_CI=1`) Nitro defaults `cloudflare.deployConfig` on, writes `.output/server/wrangler.json` and redirects `wrangler deploy` to it through `.wrangler/deploy/config.json`: the app and `/api/notion/*` would go live without the gate. `nuxt.config.ts` sets `cloudflare.deployConfig: false`, and `build:cloudflare` ends in `scripts/check-cloudflare-bundle.mjs` (a `wrangler deploy --dry-run` without `-c`, as the dashboard runs it; fails on a redirect or a bundle without the gate); `npm run deploy` also passes `-c wrangler.jsonc`. A local `wrangler dev` check misses this: `WORKERS_CI` is unset there (`WORKERS_CI=1 npm run build:cloudflare` reproduces the CI path).

## Limits checked (Workers Free)

Worker bundle 901 KiB, 210 KiB gzipped (limit 3 MB compressed); 217 static files (limit 20,000); static asset requests are not counted against the 100,000 requests per day; the routes mostly wait on Notion and GitHub (waiting is not CPU time, limit 10 ms). Over a limit requests fail; there is no overage bill.

## Consequences

- Two hosts serve the same app: Vercel and the Worker. The desktop app posts its feedback to the Worker since #281 (installed versions of before still post to Vercel).
- Pitfalls of the build image: its npm must match the lockfile's npm (`packageManager` in `package.json` says `npm@11.19.0`, the version kan-do installs with), and `compatibility_date` must not be newer than the workerd of the pinned `wrangler` (`wrangler.jsonc` says which).
- Local checks: `.dev.vars` (git-ignored) holds a dummy `GATE_SECRET`, `npx wrangler dev --port <free port>` serves the built Worker.
