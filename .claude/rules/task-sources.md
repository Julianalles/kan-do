# Task source rules (ADR 015: sources, add target, pending sync, move, mixed board, merge)

Task identity (`id` vs `externalId`) and routing by `task.source`: root `CLAUDE.md` "State Management".

- **`boardConfig.sources`** (`{ connected, default } | null`; Local implicit, `null` = never onboarded) replaced `taskService`: read it through `boardStore.defaultSource` / `isIntegrationConnected(id)`, write it through `setSources` / `setSingleSource` (the one-source flows, which switch) or `connectIntegration` / `disconnectIntegration` (via `useSourceConnections`, which also fetches, flushes and clears credentials; a connect never sets `pendingSourceSwitch`; ADR 015 "Connect and disconnect"). Old data is mapped by the idempotent normalisers in `lib/taskSources.ts` (hydrate-time in the stores' `afterHydrate`, plus the desktop envelope migration 1 -> 2 using the same functions).
- **Add target (#321):** `pages/tasks/add.vue` creates through `useTaskSync().createTask` in `useAddTarget().targetSource` (reset to the default source each time the sheet opens; the ad-hoc add always uses the default and shows no switch). The "Speichern in" line is `AddTargetSwitch`, registered as the sheet footer's `lead` (`useModalFooter`); form rows come from `utils/sourceFields.ts` (`fieldsForSource`), so a source's missing fields are neither shown, saved nor mirrored to the draft, while typed values stay in the form. A create while the source needs attention or the browser is offline never calls the adapter: the task is made with a `local_…` id, `externalId: null` and `pendingSync`, and the next push creates it (`pushTask`). A Local topic's colour is derived on read (`useTopicColor`), never stored.
- **Pending sync (#319, ADR 015 addendum):** a non-Local task with changes its source does not hold carries `task.pendingSync { since, attempts, lastError }`; `useTaskSync.runSync` sets it before every write and clears it on success (`clearPendingSync(id, revision)`, so an edit during the push keeps it), `syncPendingChanges` retries it. Tracked time still queues in `pendingTimeUpdates` (only for sources that store time, `sourceSyncsTime`), and `isSyncPending(id)` covers both. The card cloud shows while the source is not healthy or the task's own push was refused (`pendingSync.lastError`); a push in flight without an error shows none (`useSavePending`).
- **A create with an unknown outcome (#528):** `NotionClientAPI` never re-sends `POST /pages` after a timeout, a network error or a 5xx (a 429 refused it first, so that retry stays). `useTaskSync` marks the never-created task `pendingSync.createUncertain { since, at, title }` (`createOutcomeUnknown`, at its three create sites: `createTask`, `pushTask`, `createMovedTask`). Two places then look for the page (`lib/createLookup.ts`, one rule: same title, created since the doubt less 5 min, not in `tasksStore.claimedPages`: cards, pending deletes, move origins, deleted ids): `mergeTasks` hands a fetched page to the waiting task before it adds a card (`adoptLandedPages`: otherwise the fetch makes the card, the page is "held" and the push creates a second one), and `NotionSource.create` queries for it (`NotionIntegration.findLandedPage`) and adopts it. A lookup that finds nothing creates only after `CREATE_LANDING_WAIT_MS` since the last attempt (the proxy may still be waiting on Notion): before that `CreateWaitingError`, a quiet "not yet" (no failure record, no toast). A failed lookup or adoption (`CreateLookupError`) creates nothing and leaves the doubt as it was. Any new code that creates a Notion page must go through `NotionSource.create`. **The doubt outlives its task (#538, #535):** a restore's create (`NotionSource.restore` goes through `create`; `restoreTask` writes `trash entry.createUncertain` when only the create request ended unknown, every other restore failure is `CreateLookupError`, i.e. no create sent) and a deleted or moved task's create (`pendingMove.fromCreateUncertain`, the pending delete's `pendingSync`) keep the same marker shape. A delete or a move's origin removal settles it through `TaskSourceAdapter.removeLanded` (Notion: the lookup, then archive; `CreateWaitingError` / `CreateLookupError` keep the delete or move queued without a toast), and a page is archived only when the lookup identifies it and no other doubt of the same title exists (`tasksStore.hasCompetingDoubt`, trash entries too); `adoptLandedPages` also hands a fetched page to such a pending delete or move origin, so no card appears, but only when `hasCompetingDoubt` finds no rival (a card, delete, move origin or trash entry of the same title): with one the page is left alone (it may be the rival's). **A trash entry with a doubt is a waiter too (#545):** a fetched page goes to it (`trashStore.takeLandedPage`: `task.externalId`, doubt dropped) and a queued pending delete archives it (the page is in `deletedTaskIds`, no card); the restore then cancels that delete or un-archives the page, never creates. The same rival rule applies; an entry whose restore is in flight (`restoresInFlight`, part of `isPushing`) is skipped. **A write that resolves settles the window (#555):** a fetch that lands while a create or restore is in flight cannot be told whose page it is, so the card it made stays for that moment; `tasksStore.dropLandedDuplicates(source, externalId, exceptTaskId)` (called by `completeCreate`, `completeMoveCreate`, `createTask` and `restoreTask`, then the statistics records go) drops every other card of the page the write stored that holds nothing the source lacks (no `pendingSync`, queued time or `pendingMove`: another waiter a fetch handed the page to keeps its notes and time, so two cards may stay), and the waiting task keeps its `id`. Local only: nothing is archived or remembered in `deletedTaskIds`. Any new code that stores a page a create or restore made does the same before it adds or completes the task.
- **A 429 pauses the source's pushes (#529):** a rate limit is the source's, not the task's. `reportPushFailure`, `deferMove` and the origin removal note it (`rateLimitOf`, `NotionAPIError.retryAfterMs`); `useTaskSync` then skips that source until `Retry-After` (else `RATE_LIMIT_WINDOW_MS`) has passed, in `syncPendingChanges`, the create loop of `syncArchiveStatusForTasks`, `createMovedTask`, `writePlanning`, the batch `updateTaskStatuses` (`holdWhenRateLimited`: the status change stays, marked) and `createTask` (queued like an offline create). In memory only; the markers and their order stay; health is not touched (`pushFailureScope` keeps a 429 in the `task` scope). A loop that stops early must leave every task it does not send with a marker (`syncArchiveStatusForTasks` marks the rest when it breaks: its archive is local at once and has no marker of its own). A single user-made write (`updateTaskStatus`) still sends. Any new push loop over a source's tasks checks `isRateLimited(source)`. A delete that meets a 429 is queued like an offline one (`commitTaskDelete`, #543: `noteRateLimit`, then `state: 'queued'`, no toast; a queued delete sends nothing inside the window) and `syncPendingChanges` commits the queued deletes of a source outside its window (start and reconnect alone would leave it queued); `commitTaskDelete` also drops the trash entry when it restores a task for good.
- **Move between sources (#322, ADR 015 addendum):** "Verschieben nach …" (card menu, detail dropdown, palette "Verbindung" group; one list from `useTaskMoveTargets`) runs `useTaskMove().moveTaskToSource`: local re-assignment at once (`tasksStore.reassignSource`, `pendingMove`), undo toast through the shared `useUndoWindow` (delete uses its toastless `beginTimed` mode), and only after the toast closed `useTaskSync.commitTaskMove` creates in the target, then removes the origin copy. `pendingMove` with `externalId === null` = create outstanding, with an `externalId` = origin removal queued; a rejected create reverts and raises `lib/taskMoveEvents` (failure toast with retry). Never push a moved task through `pushTask`/`adapter.update` while `isMoveHeld` or its create is outstanding (`runSync` routes it).
- **Mixed board (#323):** `tasksStore.hasMultipleSources` (distinct `task.source` among the stored tasks `>= 2`, derived, not from `sources.connected`) turns on the 16px `TaskSourceIcon` at the start of every card footer (Erledigt too, never the add-sheet draft) and drops Notion `custom:*` grouping options (topic, activity and priority stay) (`utils/groupingOptions.ts`; `pages/tasks.vue` falls a persisted `custom:*` key back to topic). Footer width rule: the comment at the card footer in `TaskCard.vue`. Seeds: `WORST_CASE_FOOTER_TASKS` (`tests/e2e/helpers/seed.ts`).
- **Features on a mixed board (#325):** every per-task path follows `task.source`, never the default source: delete (`PendingTaskDelete.task.source`, the carry-over label), "Gesehen" (`syncArchiveStatusForTasks`), the sheet (`customList` is Notion's, empty for a Local task). Statistics, day close and the palette are source-blind; export/import carry `source`/`externalId` and `boardConfig.sources`, tokens never, so an imported Notion source is `broken` until reconnected. Sequence specs: `tests/e2e/mixed-board-features.spec.ts`, the requirements walk `mixed-board-requirements.spec.ts`.
- **Trash and delete (#422, ADR 015 addendum):** a delete (`useTaskDeletion.deleteTaskWithUndo`) takes the task out of `tasks` at once and keeps its slot as a gap (`pendingDeletes[id].slot`, rendered by `TaskDeletedGap` from `useDeletedGaps`, never inside `SortableTaskWrapper`) for the 5 s window (`useUndoWindow.beginTimed`, paused by hover/focus). `closeDelete` moves the snapshot into `store/trash.ts` and commits upstream as before (a commit that fails for good restores the task and drops the entry); the entry exists from the window's close, also while the commit is queued offline. Restore is `useTaskSync.restoreTask`: `TaskSourceAdapter.restore` first (Local re-add, Notion un-archive or create, Todoist create with a new `externalId`, same `id`), then one synchronous step (`undeleteTask`, add, `restoreGuard`, carry-over, entry removal); a still-queued delete is cancelled instead. A task from Jetzt restores into Offen. Remove-forever and "Papierkorb leeren" never touch the source. `restoreGuard` (transient) makes `mergeTasks` keep a restored task a stale fetch lacks.
- **Not planned (#353, epic #334):** `task.notPlanned: true` (absent = planned, valid only while Open) holds a task off today's board. Read it only through `isNotPlanned()` (`lib/taskPlanning.ts`); change it only through `useTaskSync.planTask` / `unplanTask`. It is kan-do's own state: no fetch delivers the marker itself, `mergeTasks` keeps the held task's marker (unless the source's own planning state changed, next rule), and every status write drops it unless the task stays Open. A reader that means "on today's board" uses the column getters (`tasksOpen` excludes it) or filters with `isNotPlanned`; a reader that means "a task kan-do holds" (`tasks`, counts, topic options, `hasMultipleSources`) includes it. Not `isUnplanned` (ad-hoc work). Order of "Meine Aufgaben" (#354): `tasksStore.tasksNotPlanned` lists the tasks put back by hand first, newest first (`boardStore.notPlannedOrder`, persisted, pruned in `reconcileColumnsWithTasks`), then the rest in stored order. Several at once (#356): `useTaskSync.planTasks` / `unplanTasks` (one reconcile, the order given); the rule "a marker survives only Open to Open" is `markerSurvives()` for every status writer. **The day close (#480)** takes the same tasks off the board on the user's click in the evening through the same `useTakeOffBoard().takeOffBoard()` (`useDayCloseAction().finishDay`), then `markDayClosed` marks the next day as started with the Jetzt and Offen ids as its group (rule: `.claude/rules/persistence.md` "New day"). **The fresh start (#387; it replaced the automatic pass of #356):** the app takes no card off the board by itself. `composables/useNewDay.ts` has `check()` (the day check `pages/tasks.vue` runs on the app's start and on a return after an absence: it moves nothing, only the baseline, the time question and the notice's offer) and `freshStart()` (the user's click: "Tag neu planen" in the recap, the notice's button), which takes Jetzt, Offen and Wartet off the board once per local day through the status path and `unplanTasks`, stores the Jetzt and Offen ids in `day-recap-store.sentBack` and the Wartet ids in `sentBack.waiting` (the panel "Gestern auf dem Board" holds both for that day only, #469; an earlier start's Wartet task is a plain "Weitere Aufgaben" task); resolve Nuxt-bound composables in `useNewDay()`'s setup, never inside `check()` or `freshStart()` (the check also runs from a window event). The UI moves go through `usePlanMoves()` (`planForToday`, `notToday`: motion and the screen-reader line around the two `useTaskSync` calls). A snapshot put into another column (restore, undo into Offen) goes through `inStatus()`, so a stale marker never hides it; a deleted not-planned task has no gap slot and returns to "Meine Aufgaben".
- **A source's own planning state (#357):** `task.sourceNotPlanned` is what the source holds the task as while it holds it as not planned (the Notion status name from `statusMapping.notPlanned`; absent = planned or no planning: Local, Todoist). A fetch delivers it, never the marker. `mergeTasks` moves a task only when the fetched value's presence differs from the stored one: a task seen for the first time starts where its source holds it, the same answer as last time leaves kan-do's marker alone (so a put-back the source never heard of survives every sync: Notion without a mapped status, a card the pass of #356 put back), a task with `pendingSync` keeps its local value. The user's plan and put-back, the fresh start included (#387), go through `useTaskSync.planTasks` / `unplanTasks`, which write to a source only when its adapter answers `notPlannedHold()` (Notion with a mapped status: the value is set or cleared, the task marked pending at once and pushed, one after another); there is no move that stays local any more. Every status writer that drops the marker (`markerSurvives`: `updateTask`, the batch move, `inStatus`) drops `sourceNotPlanned` with it, because that write tells the source the column; a stale value would make the next put-back skip its write. Notion writes an Open task as its `sourceNotPlanned` only while it is not planned and the status is still mapped (`statusNameFor`), else as `today`. Never set the field elsewhere; a move to another source drops it and keeps it in `pendingMove.fromSourceNotPlanned` for the undo. **Todoist** has no planning state: its adapter says `startsNotPlanned`, so only an Open task kan-do sees for the first time starts not planned, and a fetch never moves a card kan-do already holds (#387: the app moves no card by itself); `holdsOnlyOpenDone` keeps a local Jetzt or Wartet when the source says open. **Capped list:** the Notion "not planned" query is separate, sorted by last edit and capped (`lib/notionLimits.ts`, `notionConfig.notPlannedLimited` says when Notion has more); the board query is never capped. A capped fetch is a part, not the whole: the adapter hands the manager `FetchedTasks.partialNotPlanned` (`fetchActiveList`, per fetch), and `mergeTasks` keeps a task held in one of those statuses that the list lacks, and a task with `pendingSync`, as they are. Never merge a capped list without it: the merge would drop held tasks with their unpushed edits. **Two reads:** the board query is read before the "not planned" query, so a write that takes a page out of "not planned" (a plan, a move from "Meine Aufgaben" into a column) is in neither answer when it lands between the two reads, capped or not. A list therefore says "gone" only for a task it was read after: the manager hands `mergeTasks` `fetchStartedAt` and `pushing` (`useTaskSync.isPushing`), and a task of any source written since the fetch began (`writtenAt`, transient: a change noted, a push that went through or failed) or being written now stays as it is; the next fetch decides. The same holds for a task the list contains (#390): a task written since the fetch began, or being written now, keeps its local state whole (only the source's `externalId` is taken), because the list is older than the write; the card never flips back under a sync that was already on its way. A page the user moves at the source itself between the two reads is in neither answer and no write of kan-do's explains it (#392): the adapter says `FetchedTasks.readInParts` (Notion with a mapped "not planned" status) and `mergeTasks` keeps a task such a list lacks once and drops it when the next list lacks it too (`lackedByLastMerge`, transient, per source). The same one-shot ends the guard above for a task whose push keeps failing (it stamps `writtenAt` on every tick): kept for one fetch, then gone with the page. The cost: a page deleted or archived in Notion shows one sync longer. The user's "Ja" to the sync question (#369) is not an ordinary sync: the manager passes `confirmedDrop` and the keep-once does not apply to that merge (a task being written still stays), or the answer would remove nothing and the question would come back. Never call `mergeTasks` with a fetched list without `fetchStartedAt` and `pushing`; a source that reads in parts also hands `readInParts`.
- **Apple Reminders (#551, ADR 015 addendum "Reminders source"):** a source over `lib/reminders.ts` that is read-only in kan-do: capabilities are asked through `sourceCan(source, 'create' | 'remove' | 'moveOut' | 'editText')` (`lib/taskSources.ts`), never by the source's name; a recurring reminder is one task per occurrence (`externalId` `<id>@<date>`), the occurrences done today live in `remindersConfig.doneOccurrences`; `mergeTasks` takes `keepsKanDoFields` (time box, priority, ad-hoc marker stay kan-do's). A new place that creates, deletes, moves or edits the text of a task asks `sourceCan` first. **Setup and settings (#552):** the welcome flow (`RemindersSetupFlow`, state in `useRemindersSetup`) and `/settings/reminders` write `remindersConfig.lists` only at the last button (Back writes nothing; a failed connect puts the earlier answers, the connection and the never-onboarded state back), a first run onboards Local first and connects Reminders beside it (`singleSource('reminders')` and `sourceCanBeDefault`: never the default), and with Notion also ticked `useFirstRunSources` makes `connected = ['reminders','notion']`, Notion the default. A list switched to Aus in settings leaves through `tasksStore.dropSourceTasks` (not a delete: nothing is remembered in `deletedTaskIds`, nothing is pushed, Reminders is untouched), never through a refetch (the sync-drop warning would ask). **Planning by date (#553):** `TaskSourceAdapter.planningByDate` (Reminders): the date is the plan. The adapter delivers `sourceNotPlanned = 'not-today'` unless the reminder is dated today and `dayHasBegun()` (`lib/dayBegun.ts`); `mergeTasks` takes `planningByDate` and never takes a planned card off the board by a fetch; `writePlanning` writes today's date only on the user's plan (`planWrite` answers the day, `pendingSync.dateWrite` keeps it and the adapter writes only on that day, never for a recurring reminder), nothing on put-back, fresh start or day close; `planningHeld` notes the date's answer after a plan or put-back; `Task.reminders.wrote` feeds `restorePlannedDate` (the two undo toasts of `usePlanToasts`). Never write a date from any other path. ADR 015 "Reminders today sync".
- `mergeTasks(source, fetched)` replaces only that source's tasks (matched by `(source, externalId)`), and must preserve local time tracking and pending updates when reconciling external data. Time keeps the larger of local and fetched, except a total the user set in the sheet (kd#4, `tasksStore.setTimeSpent`): its queued entry carries `absolute: true`, so the local total wins until a push carried it, and that push writes the Notion time property even at 0 (`adapter.update(task, { timeEdited: true })`). A source that holds time rounded to a unit (Notion minutes/hours) hands `mergeTasks` `heldTime` (`TaskSourceAdapter.timeHolding`): a fetched value equal to the local total as the source holds it keeps the exact local seconds and queues no push (#323). A source whose time property takes no number (a Notion select, `TaskSourceAdapter.timeWritable` false, #331) gets no time write in `updateTask` and no queued push from the merge

## Identity

- **Task source and identity** (ADR 015): every `Task` has `source` (`'local' | 'notion' | 'todoist' | 'reminders'`) and `externalId` (`string | null`). `id` is the stable app-level identity (statistics, order, carry-over, archive, timers and routes are keyed by it) and never changes; integrations receive `externalId`, never `id` (`externalIdOf()` in `lib/taskSources.ts`). `useTaskSync` routes by `task.source`. `boardConfig.sources` replaced `taskService`; read and write it only as `.claude/rules/task-sources.md` says.
