# Desktop (Tauri) rules: desktop E2E stub, CSP, in-app feedback

Running the desktop app or rendering desktop-only pages: the `desktop-verify` skill. Data file and `cargo test`: `.claude/rules/persistence.md`.

- **Desktop (Tauri) E2E**: specs fake IPC via `tests/e2e/helpers/tauriStub.ts` (`mockIPC` cannot run in `addInitScript`); `installTauriStub` fakes the `data_*` commands, no real file; a desktop spec that needs a board puts it into the stub's data envelope, which wins over seeded localStorage. Keep the stub in step with the Rust commands it fakes; `tests/config/tauri-stub-contract.test.ts` fails when a command in `generate_handler![...]` has no stub branch.
- Desktop CSP (`docs/adr/012-desktop-csp.md`): a new host the *webview* calls needs a `connect-src` entry in `csp` and `devCsp` (plus `capabilities/default.json` when it goes through the http plugin) and a `tests/config/tauri-csp.test.ts` update; GitHub and release hosts are Rust-side and must stay out. CSP breakage shows only in the built bundle.
- In-app feedback (#227; web too since #268): palette "Feedback senden" → `FeedbackDialog` + element picker (`useFeedback`, `useElementPicker`, `lib/feedback/`); three send routes (`sendRoute`): the owner's token (the `gh` login after the opt-in marker `developer-feedback` in the app config dir, else a Keychain token stored earlier; ADR 007 amendment #280) through `github_request` only, everyone else through the relay `POST /api/feedback` (`lib/feedbackRelay.ts` → `server/utils/feedbackRelay.ts`, private repo `jaylouiz/kan-do-feedback`, server-side `FEEDBACK_GITHUB_TOKEN`), the prefilled GitHub link only as the fallback; E2E answers the relay with `tests/e2e/helpers/feedbackRelay.ts`, never a real one; memory-only draft, component names from the `data-component` marker plugin; optional screenshot (#247): native `feedback_capture` (`src-tauri/src/capture.rs`) → `useScreenshotCapture` (mask `[data-private]` for the capture only) → `FeedbackAnnotator` canvas → upload to the orphan `feedback-assets` branch; Rust pins the feedback token's writes to issues and that branch — see `docs/adr/010-in-app-feedback.md` and `docs/adr/014-feedback-screenshots.md`.
- **Native menu bar and overscroll** (#614, `docs/adr/018-native-menu-and-overscroll.md`): macOS menu from `src-tauri/src/menu.rs` (`menu_install(labels)`, labels = i18n `menu.*`, custom clicks as the event `menu://action`), mapped in `lib/nativeMenu.ts` / `composables/useNativeMenu.ts`; a new item needs its id in Rust `MENU_ACTIONS` and `MENU_ACTION_IDS` (`tests/config/native-menu-contract.test.ts`) and must not take a shortcut the web app handles. Desktop-only CSS keys on `html[data-shell="desktop"]` (`plugins/desktop-shell.client.ts`). The window has no title bar (`titleBarStyle: Overlay`, traffic lights in the app bar row); the `.titlebar` strip in `app.vue` is the drag area and needs `data-tauri-drag-region` plus the `core:window:allow-start-dragging` permission (`tests/config/tauri-window-chrome.test.ts`); full-screen layers cover the strip, so a press in the bar row on a Nuxt UI scrim (`data-slot="overlay"`) or on the empty area of a custom layer marked `data-window-drag-layer` (NewDayRecap; set it on any new full-screen layer) starts the drag from `plugins/desktop-shell.client.ts` (`lib/windowDrag.ts`), and desktop content must not sit in that row under the strip (the welcome notice starts below it). `native-menu.spec.ts` plays `menu://action` through `emitTauriEvent`; the real menu bar contents need a frontmost window, so they stay a manual check.
- **Floating Now window** (#383, `docs/adr/020-floating-now-window.md`): a second Tauri window (label `overlay`, route `/overlay`) owned by `src-tauri/src/overlay.rs`; the main window pushes the Jetzt task (`composables/useNowWindowSync.ts` → `overlay_sync`), Rust shows the pill iff the setting is on and a task is shown (Jetzt, or the one paused from the pill), whichever window has the focus (#436; `overlay::should_show`; a press on the pill activated Kan-Do, so hiding on focus made it unmovable; the window is also non-activating, `overlay::make_non_activating`, so a press does not raise Kan-Do or take the keyboard focus), as system glass (`effects`: Liquid Glass, vibrancy fallback), the pill's clicks come back as `overlay_action` (`open` in Rust, `toggle-pause` and `done` as the event `overlay://action`). The pill window must never touch data: `app.vue` mounts only the pill there (`lib/overlayWindow.ts`), a new client plugin either returns early on `isOverlayWindow()` or is listed in `tests/config/overlay-contract.test.ts`, a new `data_*` command takes `window: tauri::Window` and calls `ensure_main_window`. Names shared with Rust (label, events, `OVERLAY_ACTIONS`) live in `lib/nowWindow.ts`; the position is machine-local (`overlay-window.json` in the app config dir, never the data file). `now-window.spec.ts` plays the stub; the real window (the glass look, drag without raising Kan-Do or taking the focus, first click, full-screen apps) is a manual check.
- **Native feel** (#370): the desktop app is not a web page. Under `html[data-shell="desktop"]` all text is `user-select: none` (`assets/css/utilities.css`) except text fields and content marked `data-selectable` (task text is edited in fields; errors, paths, ids, release notes are marked): mark any new text the user may copy, never `data-private` (that is the screenshot mask). The board keeps its own `none` (#285). In a production desktop build (`isTauri() && !import.meta.dev`) `plugins/desktop-shell.client.ts` cancels the browser context menu except in text fields and on selected text (`lib/nativeContextMenu.ts`); it never stops propagation (the task card menu). The web app and dev builds keep the browser defaults. `desktop-native-feel.spec.ts`.
- **Native feel, more** (#398, #393): the same production-only block cancels the `keydown` of reload (F5, mod+R), print (mod+P) and page zoom (mod with + = - 0) through `lib/nativeShortcuts.ts`, where mod is Cmd on macOS and Ctrl elsewhere (macOS Ctrl+P / Ctrl+N are text bindings and pass); never `stopPropagation`; WKWebView binds none of them, so on macOS it is a safety net; `zoomHotkeysEnabled: false` is pinned in `tauri.conf.json`); links and images are not draggable under the desktop marker (`-webkit-user-drag`, `dragstart` fallback). Pressable controls show the arrow cursor under the marker (unlayered block in `utilities.css`: beats the base layer's hand and Tailwind's `cursor-pointer`; `not-allowed`, the drag and picker cursors are `!important` or excluded; a link in `data-selectable` text keeps the hand; the specificity stays above a scoped class rule on purpose, so a control with a deliberate cursor, `cursor-text|grab|not-allowed`, is excluded by name in the `:not()`); a new class that sets `cursor: pointer` on a non-control element (the card `.task`, table rows) joins the selector, a new deliberate cursor joins the `:not()`. The main window's size, position and screen mode are restored by `tauri-plugin-window-state` (`src-tauri/src/window_state.rs`: flags without `VISIBLE` and `DECORATIONS`, the Now window denied; `.window-state.json` in the app config dir, machine-local, never the data file; Rust-only, no capability).
